# Design

screendoc records terminal sessions and derives reviewable artifacts from
them: videos, still frames, searchable text, and a live web player. This
document describes the architecture and the guarantees the design makes.

## Crate layout

```
screendoc/
├── crates/
│   ├── sdoc-core/     # event model, session store, cast I/O, markers, redaction, encryption
│   ├── sdoc-record/   # recording: tmux wrapper, pane groups, shell hooks, ambient mode
│   ├── sdoc-render/   # frame rasterization, ffmpeg video pipeline, web player
│   └── screendoc/     # the `screendoc` binary: CLI, command wiring, UX
└── examples/          # runnable end-to-end walkthroughs (also a CI smoke test)
```

Dependency direction is strict: `screendoc` → `{sdoc-record, sdoc-render}` →
`sdoc-core`. Nothing depends on the CLI crate, and the renderers/recorders
only talk to core through its public API, so every hot path is unit-testable
without spawning a process.

## Data model

A session is a directory under `~/.screendoc/sessions/<id>/` containing:

| File | Contents |
|---|---|
| `meta.json` | id, start time, mode, command, duration |
| `raw.cast` | asciinema-format terminal byte stream (what the screen showed) |
| `events.jsonl` | structured events: commands, exit codes, chapters |
| `markers.jsonl` | raw shell-hook markers, demuxed into `events.jsonl` |
| `frames/` | optional rasterized stills |

`id` is `timestamp-pid-counter`: opaque, sortable, and unique within the
machine. The cast stream is the source of truth for *what was shown*;
`events.jsonl` is the source of truth for *what was run*.

## Event and marker flow

Shell hooks (generated by `screendoc hook-script`) append escape-sequence
markers (`OSC 1337;SCREENDOC;…`) into the terminal stream around command
boundaries. The recorder's `MarkerReader` demultiplexes the byte stream in
one pass: markers are split out and parsed into `MarkerRecord`s; everything
else is written to `raw.cast`. This means the cast never contains marker
bytes, and the markers carry the data (`command`, `exit_code`, `seq`) the
cast alone cannot.

Automatic chapters are derived from commands (shortened command text);
manual chapters come from `screendoc chapter`. Both live in `events.jsonl`
and drive chapter markers in rendered videos.

## Render pipeline

```
raw.cast + events.jsonl
   │  parse_cast (frame.rs)
   ▼
vt100 terminal model stepped per output event, rasterized per frame
   │  Frame::render (cell grid → RGBA with the active color theme)
   ▼
PNG frame sequence ──► ffmpeg
                        ├── GIF (palettegen/paletteuse, bayer dither)
                        ├── MP4 (H.264, crf 20, faststart)
                        ├── WebM (VP9, crf 30)
                        └── AV1 MP4 (crf 32)
```

Terminal size resolution: the last valid resize event wins; otherwise the
cast header's recorded dimensions; otherwise the configured default
(120×30). This matters for recordings made with an explicitly sized wrapper
(`--size 80x24`): the renderer honors what was recorded.

Idle frames are compressed (`compress_idle`): stretches longer than
`idle_limit` (default 2 s) collapse to a short hold, keeping videos short
without losing content.

## Encryption

`--encrypt` (or `encrypt = true` in the config) stores the content files as
AES-256-GCM record streams under a 32-byte key at `~/.screendoc/key`
(mode 0600). Reading is transparent: `Session::cast_text()` and friends
decrypt in memory, so redaction, search, and rendering work unchanged.
Session directories are 0700 on Unix; a session captures a terminal, which
is assumed to contain secrets.

## What is guaranteed, and what is not

- **Guaranteed:** the cast + events logs are well-formed and independently
  verifiable; redaction is applied in place to *all* stored copies of a
  session (cast, events, and rendered artifacts are regenerated from the
  redacted source); encrypted files are unreadable without the key.
- **Not guaranteed:** redaction of derived artifacts that existed *before*
  the redaction (delete and re-render), and confidentiality against an
  attacker who also holds `~/.screendoc/key`.

See [threat-model.md](threat-model.md) for the full threat analysis and
[user-guide.md](user-guide.md) for day-to-day usage.
